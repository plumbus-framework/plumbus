# Patterns & Conventions

This file defines the conventions that keep generated Plumbus frontend code predictable across generators, tests, CLI wrappers, and automated coding tools.

## Naming conventions

| Element | Convention | Example |
|---|---|---|
| Generator function | `generate{Thing}` | `generateClientModule`, `generateAuthModule` |
| Extractor function | `extract{Thing}` | `extractFormHints`, `extractFieldHint` |
| Generated React hook | `use{PascalCapabilityName}` | `useGetUser`, `useCreateOrder` |
| Generated client function | `{camelCapabilityName}` | `getUser`, `createOrder` |
| Generated type | `{PascalCapabilityName}Input` / `{PascalCapabilityName}Output` | `GetUserInput`, `GetUserOutput` |
| Generated flow trigger | `start{PascalFlowName}` | `startOrderFulfillment` |
| Generated form hint constant | `{PascalCapabilityName}FormHints` | `CreateUserFormHints` |
| Generated file | Path returned by generator | `client.ts`, `auth.ts`, `form-hints.ts`, `i18n/messages.ts` |
| Test file | `{generator-name}.test.ts` | `client-generator.test.ts` |

Use the exported naming helpers when another package needs to refer to generated names. `capabilityClientFnName(capability)` must match `generateTypedClient(capability)`, and `flowTriggerFnName(flow)` must match `generateFlowTrigger(flow)`.

## Recommended patterns

Generator inputs should use framework types from `@plumbus/core`: `CapabilityContract` for capability-based generators and `TranslationDefinition` for translation generation. Generators that emit a single file should return a source string. Generators that emit several files should return `GeneratedFile[]`.

Generated source should make its runtime imports explicit. Contract-derived modules should include `// Auto-generated by @plumbus/ui — do not edit` and should be regenerated when contracts change. Scaffold files, such as example pages or the starter Next.js shell, may be edited by the application after generation.

Auth helpers must guard browser-only APIs such as `localStorage` for SSR safety. Client functions and flow triggers should derive names and paths from contract data rather than duplicating ad hoc strings in multiple places. Translation files are allowed to import `@plumbus/ui/next-intl` and `@plumbus/ui/next-intl-server`; those subpaths are part of the package's intended runtime surface for i18n integration.

## Implementation boundaries

Business logic and authorization decisions belong in backend Plumbus capabilities and policies, not in generated frontend code. `RouteGuard` is a UX helper. The Next.js template creates a starter shell and does not generate capability pages. Generated hooks use React state/effect directly and do not provide TanStack Query caching, invalidation, or retries. Form hints come from `capability.input`, not from entity definitions. Generated source code must not embed secrets.

## Common workflows

### Generate contract-derived frontend modules

A CLI wrapper or application script can write generated modules into an app frontend:

```text
frontend/lib/client.ts
frontend/hooks/hooks.ts
frontend/lib/auth.ts
frontend/lib/form-hints.ts
frontend/i18n/*
```

These files should be regenerated after capability, flow, auth, form, or translation definitions change.

### Scaffold a starter Next.js shell

```ts
import { generateNextjsTemplate } from "@plumbus/ui";

const files = generateNextjsTemplate({
  appName: "My App",
  auth: true,
  apiBaseUrl: "http://localhost:3000",
});
```

This creates a starter app shell. It does not install dependencies and does not generate capability pages as part of the template.

### Generate example capability pages

```ts
import { generateCapabilityPage } from "@plumbus/ui";

const pageFile = generateCapabilityPage(capability);
```

Use this only for simple examples or initial scaffolding. Product UIs should normally replace or heavily edit these pages.

### Add a new generator

When adding a generator, implement it under `src/generators/`, export the public API from `src/index.ts`, add focused tests under `src/generators/__tests__/`, and update both the package README and `docs/ui/ui-generation.md`. Add or update an instruction file when automated coding tools need guidance for the new generator.

## Generated code output conventions

| Convention | Rule |
|---|---|
| Module header | `// Auto-generated by @plumbus/ui — do not edit` for contract-derived modules. |
| Client imports in hooks | Import generated clients and types from `../lib/client` or the path used by the generated app. |
| Auth imports in scaffold | Import from `@/lib/auth` when generated scaffold code expects the app auth module. |
| Error handling | Client code throws enriched errors with `status`, `code`, and `metadata` when possible. |
| Query hook cancellation | Query hooks use a local `cancelled` flag during effect cleanup. |
| Form hints | Extract from Zod object fields under `capability.input`. |
| Translation files | Emit `i18n/*` source files and import the package's `next-intl` re-export subpaths where required. |
